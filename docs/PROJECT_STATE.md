## Известные дефекты для регрессии

1. API не подтверждает Telegram initData; admin/check безусловно возвращает true, административные журналы открыты.
2. transaction(callback) делает commit до завершения async callback. Нужна единая граница операции и одно соединение.
3. Веб-призы несовместимы с awardPrizeToUser; API не проверяет асинхронный результат; React-колесо выбирает приз локально без начисления.
4. Реферальные билеты записываются в fortune_tickets, колёса читают tickets.
5. last_private_bonus_time используется в миллисекундах ботом и секундах API.
6. Платёж не защищён уникальным telegram_payment_charge_id.
7. Схема меняется при импорте, часть ALTER идёт до создания таблицы; локальная схема расходится с кодом.
8. Есть повторные объявления функций db.js, отсутствующие экспорты и неверный путь генератора партнёрских промо.
9. updateUserBalance пробрасывает ошибки; при успехе возвращает undefined, хотя часть вызывающего кода ожидает changes. Не повторять прежнее ошибочное предположение, что функция подавляет исключения.
10. Локальные данные требуют сверки: один NULL balance, 69 pending выплат. Нельзя без анализа начислять или обнулять их.

## Как обновлять память

После этапа обновлять фактический результат, выполненные проверки и следующий шаг; новые решения записывать с датой и причиной. Стабильные соглашения держать в AGENTS.md, детальный план — в migration/PLAN.md, маршруты — в migration/ROUTES.md и route-inventory.json, ручные проверки — в migration/MANUAL_TESTS.md. Если появятся самостоятельные долгосрочные архитектурные решения, выделять их в docs/decisions/ с ссылкой отсюда.

Не сохранять токены, пароли, session-файлы Telegram, персональные данные игроков и сырые строки базы. Снимки маршрутов привязаны к коммиту и устаревают после изменения кода. Память сверять с исходниками и новыми указаниями пользователя; она не доказывает текущее состояние внешних сервисов.
