# Этапы проверки на хостинге

Каждый этап: изменения и локальные проверки → коммит и push → перезапуск тестового контейнера → логи и ручные сценарии → запись результата в память. Следующий этап начинается после сверки предыдущего с пользователем. Рабочая ветка стенда — master, согласно настройке панели. Git pull выполняется при запуске, а не обязательно сразу после push.

## Этап 0 — сохранение исходного состояния

Полный локальный архив, восстановление всех файлов с проверкой SHA-256, SQLite quick_check. Git-коммит исходной документации `f8529da`, тег `pre-mysql-migration-2026-11-27`. Архив содержит секреты и не публикуется. Резервная копия файлов самого контейнера через вкладку панели «Резервные копии» дополнительно сохранит отличия стенда от локальной папки.

## Этап 1 — соединение и наблюдаемость

Добавлены mysql2, диагностический SELECT метаданных, проверка конфигурации, резервная копия SQLite перед первым запуском нового этапа и логи коммита. При включённой проверке и ошибке MySQL бот/API не запускаются. Проверка выключена по умолчанию для окружений без MYSQL_PREFLIGHT.

На хостинге открыть «Файлы» → `.env`, сохранить существующие строки и добавить блок из локального приватного `temp/hosting-mysql.env`. Полные имя базы и имя пользователя берутся из панели; MYSQL_HOST содержит только адрес, MYSQL_PORT — отдельное число. Блок исключён из Git. После сохранения перезапустить контейнер.

Ожидаемые строки в консоли:

```text
[RELEASE] {"commit":"...","stage":"01-db-connectivity","activeStorage":"sqlite"}
[SQLITE SNAPSHOT] {"status":"created-and-verified"}
[MYSQL PREFLIGHT] OK {"serverVersion":"...","databaseCharset":"...","connectionLimit":2,"activeStorage":"sqlite"}
[DATABASE] Active storage: SQLite. Stage 01 checks the target database connection only.
```

При повторном запуске snapshot получает status already-verified. Копия находится в `backups/migration/stage-01-before-start/`; там SQLite и manifest.json с SHA-256. При ошибке копирования или повреждённой копии запуск останавливается. Если база не найдена, status source-missing; это повод сверить файлы хостинга до любых действий с игроками.

`MYSQL_PREFLIGHT DISABLED` означает, что соединение не проверялось: переменная не включена. `FAILED` и код ошибки означают, что этап не пройден. ETIMEDOUT/ECONNREFUSED — проверить сеть и адрес; ER_ACCESS_DENIED_ERROR — данные учётной записи и допустимые адреса; ER_BAD_DB_ERROR — полное имя базы. Пароли и исходные сообщения драйвера не печатаются.

Дополнительно открыть существующий Mini App и `/api/health` на его домене. Поля status и timestamp сохранены; новое поле release показывает commit, stage и activeStorage. В Mini App вручную открыть профиль, финансы/карту, проверить совпадение остатков и возвраты между меню. Эта проверка подтверждает отсутствие регрессии запуска; пользовательские операции ещё не перенесены в MySQL.

Критерий сверки: commit совпадает с опубликованной версией; backup подтверждён; MYSQL PREFLIGHT OK; получена версия сервера; Mini App доступен, остатки не изменились. Для следующего этапа нужны эти строки логов и ручной результат пользователя. Права создания таблиц и финансовые транзакции на этом этапе не проверяются.

## Этап 2 — схема и пробный импорт

Создать версионные миграции в тестовой MySQL/MariaDB, импортировать актуальный согласованный снимок SQLite. Проверить все строки и связи, отдельно разобрать NULL balance, pending выплаты и расхождения счётчиков. Пользовательские операции до следующего переключения остаются в SQLite. Старые раунды в импортированной базе автоматически не оплачиваются. Тестовую базу нельзя считать актуальным вторым кошельком.

## Этап 3 — переключение операций по подготовленному релизу

Перевести все вызывающие цепочки на async и новый слой данных; локально проверить финансовые и игровые механики, API, задачи и middleware. На стенде переключать полный runtime только после совместимости всех его активных операций; не допускать разделения остатка игрока между SQLite и MySQL. Подготовительные коммиты не включают частично перенесённый runtime.

Первый ручной пакет: регистрация/профиль, карта, пополнение/снятие, переводы. Далее отдельными согласованными пакетами проверять игры, магазины/награды, партнёрку/промо, модерацию и администрирование. После каждого пакета обновлять MANUAL_TESTS.md.

## Этап 4 — восстановление и приёмка

Проверить повторы платежей и callback, конкуренцию, перезапуск во время раунда/выплаты, разрыв соединения, резервное копирование и восстановление. Повторить полный ручной прогон Mini App с хостинга, сверить имущество, историю и активный backend. Открывать бота после закрытия критических дефектов и сверки с пользователем.

## Откат

До переключения данных откатить релиз к тегу исходного состояния и сохранить текущие файлы базы. Не удалять повреждённый backup автоматически ради запуска. После новых записей в MySQL возврат к старой SQLite требует согласования данных; один git revert не переносит пользовательские изменения обратно.
