# Журналы для Mini App

Пользователь 2026-11-28 уточнил обязательный объём: Mini App должен показывать все типы логов с удобными фильтрами и последующими возможностями анализа. Это требование к хранению и API во время миграции, не только к будущему оформлению. Полный раздел ещё не реализован.

## Принцип хранения

Предметные источники остаются раздельными: кошельковый журнал подтверждает движение PF/DF, inventory_entries — предметы, finance_log — события для просмотра, игровые таблицы — раунды/ставки/исходы, message_log — сообщения. Не дублировать все строки в ещё одной огромной общей таблице и не считать текст action или произвольный JSON источником баланса. Общий интерфейс строится через серверные адаптеры с единым форматом, при этом детали каждого семейства остаются доступны отдельно.

| Семейство | Основные источники | Обязательные фильтры/связи | Готовность |
|---|---|---|---|
| Деньги, покупки, награды, промо, административные и модераторские события | finance_log, wallet_entries, inventory_entries, receipts | время, тип, участники, чат, валюта/предмет, сумма, успех, operation_key, предметный объект | Расширенный finance API готов в feature; все writers ещё нужно привести к метаданным |
| Double | double_rounds, double_bets_log, double_runtime_rounds, bet_history | hash, игрок/чат, множитель, исход, payout_status, GAME-выбор, время; переход раунд → ставки → выплата | Данные перенесены; админские raw SQLite-выборки и общий settlement ещё в работе |
| Dice | dice_rounds_log, dice_bets_log и исходные игровые таблицы | раунд, игрок/чат, сумма, кости/очки, исход, выплата | Предметный импорт есть, новые read API/UI ещё нужны |
| Сообщения/команды | message_log, отдельно сохранённый legacy message_logs | период, игрок/чат, команда/сообщение, текстовый поиск | Источники сохранены; общий раздел ещё не подключён |
| Боссы | boss_damage_history, boss_event_receipts, boss_reward_batches | босс, игрок, фаза/событие, награда, повтор/ошибка | Составные операции готовы в feature, админские выборки ещё нужны |
| Stars/донаты | payment_inbox, telegram_payments, player_donation_events | платёж/игрок, состояние обработки, валюта, время, связанное зачисление | Платёжный сервис готов; безопасный админский просмотр ещё нужен |
| Прочие действия/партнёрка/империя | предметные таблицы и finance_log | объект, участники, действие/состояние, время, связанная операция | Переносить вместе с соответствующей областью |

Существующий пункт UI «сообщения» в FIN_TYPES сейчас фильтрует finance_log; реальный источник сообщений другой. Это известный пробел, не готовая интеграция. Одинаковые названия message_log/message_logs не доказывают дублирование: проверить writers, время и содержимое перед объединением.

## Реализовано в текущем пакете

Миграция 025 добавила finance_log.operation_key, entity_type/entity_id, actor_name_snapshot/target_name_snapshot, schema_version и составные индексы участник/получатель/чат/операция/объект + ts/id. Снимок имени отделён от текущего имени JOIN: старую историю не следует переписывать после смены имени. Для исторических строк неизвестные снимки остаются NULL; не восстанавливать их догадками из action. В legacy actor_user_id местами получатель выплаты, а не инициатор; при проектировании общей карточки учитывать семантику конкретного типа, не переименовывать автоматически в «кто совершил».

Общий logFinance пишет новые метаданные и снимки, новая Double-ставка связывает журнал с operation_key своего wallet receipt и entity=double_round. Остальные прямые INSERT finance_log ещё нужно последовательно дополнить. Новые колонки не означают их заполненность во всех событиях.

Лабораторный settlement Double добавляет событие `double_payout` с system:double, игроком, чатом, раундом, ключом проводки, снимками имён и gross/credited/burned. Миграция 026 связывает принятую ставку с receipt списания. До активации нужно согласовать горячий retention Double с FK 024/026 и архивным чтением. Сценарий интерфейса ожидает подключения engine и фильтров.

getFinanceLogPage и защищённый admin endpoint принимают fromTs/toTs (UTC epoch ms), actorId, targetId, chatId, currencies, success, minAmount/maxAmount, operationKey, entityType/entityId; старые types/search/targetTs/page сохранены. Суммы фильтров передаются строкой, ID не преобразуются в Number. Входы проверяются, SQL-параметры связаны. limit максимум 200. Неверный фильтр возвращает 400 без SQL, ошибки БД — общий 500.

Для непрерывного списка: pagination=cursor, затем cursorTs/cursorId из nextCursor. Порядок ts DESC,id DESC; новые вставки не сдвигают уже пролистываемую историю. Старый offset режим оставлен для существующей UI-пагинации и перехода к дате. includeAuditMetadata=true добавляет метаданные в строки; без него прежняя форма ответа сохранена. Курсор не является фиксированным снимком всей базы: старые удаления/архивация или вставки задним числом требуют отдельной политики.

Существующий adminOnly/Telegram initData остаётся обязательным; расширение фильтров не открывает данные обычному игроку. Запретить в будущем клиенту выбирать произвольные SQL-таблицы/поля сортировки. Поиск по тексту, сохранённые фильтры, экспорт, общий каталог типов и переходы между всеми семействами — следующий UI/API объём, пока не реализованный этим пакетом. Прямой LIKE по огромным JSON/action не подменяет проектирование индексов.

## Сроки хранения и дальнейшее подключение

Текущий retention источников сохранён (message_log 30 дней, finance_log 365, игровые журналы 90). Требование «все типы» не меняет его автоматически. Кошельковые/инвентарные проводки, receipts и исходные архивы этой очисткой не удаляются. Для просмотра более старых событий нужен отдельный согласованный архивный read path; не сканировать миграционные JSON-архивы для каждой страницы и не обещать бессрочное хранение в горячей таблице. Сроки/архивацию каждого семейства оформить перед включением полной админки.

До завершения миграции: дополнить metadata остальных writers, перенести оставшийся raw SQL админских Double/Dice, добавить адаптер сообщений и каталог доступных типов/фильтров, проверить права и скрытие чувствительных полей платежей, связать карточки операций и сделать нагрузочные проверки запросов на объёме данных. Индексы текущего пакета проверены функционально; EXPLAIN/нагрузочный профиль всех сочетаний ещё не выполнен. Внешний вид Mini App пока не менялся.

Проверки текущего пакета: 132 локальных теста, MariaDB 232 SQL-сценария (35+197), 76 сравнений и все профили. Четыре новых SQL-сценария: сочетание фильтров, метаданные/снимок имени, cursor с одинаковыми ts и вставкой после первой страницы, неверные входы/SQL injection как значение. Startup восстановлен, health 200 на master/SQLite. Настоящие WebView/Telegram-запросы пока не проверены.
