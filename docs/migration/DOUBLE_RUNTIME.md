# Double: состояние переноса

2026-11-28. Feature stage03-runtime; рабочий master всё ещё SQLite.

## Готовый пакет: хранение и приём ставки

doubleRounds переносит 11 старых функций: createDoubleRound/getDoubleRoundByHash/finishDoubleRoundLog, getDoubleBetsByRound/logDoubleBet, getDoubleRoundState/setDoubleRoundState, getDoubleNotification/markDoubleNotificationSent/cleanupDoubleNotifications, updateGameChoicesForRoundUser. Чтение сохраняет типы/JSON и порядок ts,id; большие суммы остаются строками. Повреждённый JSON состояния теперь вызывает DOUBLE_STATE_INVALID вместо null: нельзя молча начать новый раунд поверх незавершённых ставок.

placeDoubleBet атомарно сохраняет PF-дебет, double_bets_log, максимальную ставку, cooldown, finance_log, wallet ledger и receipt. Ключ — Telegram update_id, actor/chat/round/multiplier/amount входят в hash. Повтор возвращает прежнюю ставку, другой запрос с тем же ключом отклоняется. Ошибка после дебета или журнала откатывает всё; компенсирующий отдельный возврат из handleBet удалён.

Под lock double_round_state и double_rounds проверяются текущий hash, ACCEPTING, active и время. При обычном результате ставки закрыты за 5 секунд, при результате GAME — за 20 секунд независимо от множителя конкретной ставки, как в исходнике. Минимум 1 PF; только рекламируемые x2/x3/x5/GAME (прежде callback принимал и произвольный xN, который никогда не выигрывал). Игрок/бан/активный Double-чат проверяются в БД. Cooldown 1 секунда на игрока+множитель между чатами сохраняется и после restart; миграция 023 double_bet_cooldowns. Исторические даты ставок не используются как новый cooldown. Повторные самостоятельные GAME-ставки разрешены: старый activeGameBets был лишь временной защитой конкурирующего вызова, а не ограничением на весь раунд.

Оба живых пути передают update_id: handlers/double.js для текста и bet_* callback в bot.js. DoubleGame.handleBet стал общим gateway; сумма/множитель команд и публичные кнопки не переименованы. Имя для журнала берётся из сохранённого игрока. Дебет не обрезает уже превышенный legacy PF-баланс. Общая статистика ставок не увеличивается при приёме: исходный код делает её при расчёте, здесь меняется только max_bet_amount.

## Следующий обязательный пакет: расчёт и восстановление

Продолжение статистики: 024 вводит double_runtime_rounds с plan_json/payout_json и double_statistics_batches. createDoubleRound помечает только действительно новый INSERT; импорт старых паспортов marker не создаёт. applyDoubleRoundStatistics требует payout_json, проверяет исходы строк, выполняет статистику/историю/batch атомарно и повторно не увеличивает счётчики. Перенесены 4 leaf-функции updateRoundStatistics/updateDoubleStatistics/saveBetDetails/getDetailedStats; они нужны совместимости, но не заменяют высокоуровневый batch.

Для следующего денежного сервиса: сначала под блокировкой подготовить и сохранить plan_json (GAME-ячейки/финальные множители/отсутствующие выборы/конфетные броски), отдельно от применения денег. Затем одной транзакцией проверить происхождение/списание каждой новой ставки, начислить PF/рефбанк/конфеты, записать исходы и payout_json, вызвать applyDoubleRoundStatistics через тот же runtime executor. При SQL-ошибке до commit plan остаётся прежним, деньги/статистика откатываются. После commit повтор должен вернуть сохранённый результат, а не заново выбирать случайность. Пока этот денежный сервис не реализован, _resolveRound остаётся в работе и полный backend заблокирован. Нужны также безопасный refund, защита старых 66 pending и переподключение сообщений/восстановления.

Проверки статистики: 130 локальных тестов, 228 SQL-сценариев (35+193), 76 сравнений и полные профили. 7 новых SQL-сценариев используют fixture payout_json без реальной выплаты, проверяют группы/максимум/20 повторов/отказы и rollback всех счётчиков/истории при ошибке batch. Не выдавать эту имитацию подтверждения за тест денежного settlement.

Продолжение: зависимость реферального банка готова в src/services/referrerBank.js. Четыре прежних метода + creditReferrerBank; начисление/снятие под lock, точные проценты и floor, лимит из config, ledger/finance_log/receipt при снятии. Внутри settlement использовать creditReferrerBank({referrerId,winAmount,operationKey}) с ключом конкретного раунда/группы, а не совместимый addToReferrerBank с random key на вызов. Переполнение исходного лимита не вызывает отрицательный added; дробный остаток не округляется при снятии и требует отдельной сверки. Два UI-пути снятия уже передают Telegram update_id. Проверено 129 локальных тестов и 221 SQL-сценарий (35+186), 76 сравнений/полные профили; сам settlement пока не подключён.

Это НЕ готовый полный Double runtime. Приём новой ставки защищён, но _resolveRound/_buildChatResult/_applyRoundStatistics/recordGameChoice ещё используют раздельные операции. Финальный фасад блокирует включение DB_BACKEND=mysql до завершения всего API.

Выявленные исходные риски:

- updateDoubleBetOutcome помечает paid/lost до updateUserBalance; отказ выплаты может оставить paid без денег. processedChats ставится до отправки, а не является транзакционным подтверждением выплаты.
- При повторном _resolveRound статистика может начислиться снова; отдельного receipt на игрока/раунд нет. Ошибки большинства шагов проглатываются.
- refundBetsForRound возвращает деньги отдельными вызовами и затем помечает все строки refunded, независимо от успешности каждого начисления. Нельзя переносить это как денежный сервис или повторять при неизвестном результате COMMIT.
- GAME-выбор, случайный выбор при отсутствии ответа, finalMultipliers и конфетный бонус должны быть сохранены до денежного результата, чтобы повтор не менял приз.
- Старые 66 неоднозначных pending-выплат из согласованного снимка сохранены как migration issue. Не считать pending/paid достаточным доказательством отсутствия/наличия старого начисления. Автоматического воспроизведения исторических выплат сейчас нет; перед cutover нужна отдельная сверка и граница раундов/обработанных updates.

Далее: явное происхождение новых MySQL-раундов/ставок, транзакционный settlement/refund с receipt, сохранение результатов/выборов, победы/реферальный банк/конфеты/статистика одним commit, сообщения после него. Затем переподключение _resolveRound и восстановление при restart. Не применять новый settlement ко всем импортированным строкам без проверки истории.

Правила, которые нужно сохранить из _buildChatResult/_applyRoundStatistics:

- Выплата группируется по игроку+чату+множителю. Обычный выигрыш — совпавший x2/x3/x5; при GAME выигрывают GAME-ставки с выбранным L/R-множителем. Один глобальный выбор игрока переиспользуется между чатами; если выбора нет, его случайный результат нужно сохранить один раз.
- Конфеты: для каждой выигравшей одиночной ставки >=100000 PF шанс 25%, количество 1–6. Банк реферовода начисляется от выигрыша; лимит/проценты по config.js и исходным функциям, требуется отдельный перенос точной дробной арифметики.
- Статистика: один total_rounds на игрока за весь раунд; группы игрок+множитель объединяют чаты. Любимый множитель и bet_history — по одному на такую группу. max_win_amount — по одиночной строке, GAME wins — один раз за раунд. Серия увеличивается только при единственном множителе во всех чатах и победе, иначе обрывается.
- Обычный раунд длится 60 секунд; шаг timer 500 мс, GAME-выбор открывается за 15 секунд и закрывается за 5. Не менять вероятности x2/x3/x5/GAME и ячеек вместе с техническим переносом.
