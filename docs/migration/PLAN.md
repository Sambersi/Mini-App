## Объём и оценка

Предварительный объём: 90–160 часов инженерной работы, ориентировочно 12–20 рабочих дней для одного исполнителя. Это оценка объёма, а не обязательство по календарному сроку агента. Она включает сохранение сценариев, разбор связей, устранение дублей, структуру модулей, импорт, регрессию и документацию. Уточнить после первого сквозного сценария на целевой БД. Ожидание доступов и ручного тестирования учитывается отдельно.

В исходной локальной версии: около 540 вызовов prepare, семь модулей с драйвером SQLite, 43 таблицы. Актуальный согласованный снимок хостинга этапа 2: 46 таблиц, 1489 пользователей, 314500 записей в double_bets. Перед окончательным переключением потребуется новый снимок: работающая SQLite продолжает изменяться.

## Сохранение поведения

- Перед изменением подсистемы описать команду, алиасы, аргументы, тип чата, роль, middleware, последовательность кнопок, callback, обработчик и операцию БД. Учесть deep links, успешные платежи, API, фоновые задачи и восстановление.
- Сохранить пользовательские алиасы, форматы ставок, доступ по ролям и уровням, ограничения, экономические формулы и навигацию. Изменения механик фиксировать отдельно от технического переноса.
- Удалять повторную регистрацию только после сравнения вызываемых функций, проверок доступа, порядка middleware и побочных эффектов. Текстовые совпадения и похожие имена не доказывают дублирование.
- Для каждого изменённого сценария добавить регрессионную проверку и запись в MANUAL_TESTS.md. Статический снимок ROUTES.md не означает, что маршрут достижим или проверен.
- Сохранить совместимость callback из старых сообщений там, где действие ещё действительно; устаревшие операции должны безопасно отклоняться без повторного списания.

## Целевая структура

Оставить Node.js и CommonJS. Не совмещать переход с переписыванием UI или внедрением ORM.

```text
src/
  db/                 # пул, транзакции, версионные миграции
  repositories/       # SQL по предметным областям
  services/           # операции, правила и границы транзакций
  telegram/           # реестр команд, callback и middleware
  api/                # HTTP-адаптеры к тем же сервисам
  jobs/               # фоновые задачи и восстановление
scripts/              # импорт, сверка и резервное копирование
tests/                # сценарии, интеграционные и конкурентные проверки
docs/                 # решения, состояние и ручные проверки
```

- Сохранить действующие точки запуска через тонкие адаптеры на время переноса. Внутри работающего приложения только один backend БД; SQLite остаётся источником импорта и архивом.
- Использовать mysql2/promise, явный запуск приложения после проверки соединения и схемы. Пул отдельный для каждого процесса; суммарный лимит согласовать с хостингом.
- Все запросы одной транзакции выполняются на выделенном соединении. Сервисы передают его репозиториям; запрещены скрытые запросы через общий пул внутри транзакции.
- Деньги и количества хранятся в целочисленных единицах. Дробные IMP и реферальные накопления требуют точного отображения существующей точности; не округлять старые данные незаметно. Telegram ID передаются строками; BIGINT/DECIMAL не преобразуются в Number без проверки диапазона.
- Разделить профиль, кошельки, владение предметами и статистику. Связи статусов, префиксов и оружия моделировать таблицами; JSON оставить для гибких деталей событий и сохранённого состояния. Не создавать параллельные изменяемые источники одного остатка.
- Для кошельков вести журнал изменений в той же транзакции, что и остаток. Исторические finance_log сохранить; начальные остатки новой системы отметить как перенос, не выдумывая отсутствующую историю.
- Платёж, выплата ставки, активация промо и выдача награды имеют уникальный ключ операции. Уведомления отправляются после commit и не являются доказательством зачисления.
- Миграции схемы — отдельная команда с учётом версий; бот и API не выполняют DDL при импорте модулей. Кодировка utf8mb4, правила сравнения строк выбрать с сохранением существующей уникальности промокодов и имён.

## Этапы и критерии завершения

Нумерация синхронизирована с HOST_CHECKPOINTS.md; сквозные сценарии, ранее включённые в предварительный этап 2, относятся к этапу 3 и пока не выполнены.

0. **Сохранение исходного состояния — выполнено.** Локальный архив и архивы хостинга, проверка восстановления критических данных, Git-тег.
1. **Соединение и наблюдаемость — технически проверено.** Версия MariaDB, доступ из контейнера, резервная копия перед стартом и метка релиза. Бот работает; приёмка Mini App отложена пользователем. Статическая карта маршрутов требует проверки по исходникам при переносе каждой цепочки.
2. **Схема и пробный импорт — технически выполнено.** Версионные миграции, точный архив всех исходных строк, основа профилей/кошельков/инвентаря/рефералов. Полная сверка снимка и повтор без дублей. Спорные данные сохранены отдельно; их разрешение и рабочие схемы остальных областей ещё предстоят. Сверка пользователя после этапа ожидается.
3. **Перенос подсистем и переключение — не начат.** Async repositories/services, сквозной путь «профиль → карта → пополнение/снятие», регистрация и рефералы, переводы, игры и выплаты, магазины, промо и партнёрка, модерация, API и задачи. Проверять права и отказы, обновлять ручной журнал после каждого пакета. До включения нового runtime подготовить все его активные операции, остановить записи обоих процессов и задач, импортировать свежий согласованный снимок в подготовленную чистую БД, полностью сверить и провести smoke-проверки. Не разделять действующий кошелёк между двумя БД.
4. **Восстановление и приёмка — не начат.** Конкуренция, повторные события, перезапуски, отказ БД, проверка восстановления, полный ручной прогон бота и Mini App. Открытие бота после закрытия критических дефектов и сверки с пользователем.

## Спорные данные и ограничения

- В локальной копии обнаружены один NULL в balance и 69 double_bets_log со статусом pending. Составить отчёт сверки; не обнулять и не перевыплачивать автоматически. До сверки старые раунды не запускать на автоматическое восстановление.
- tickets/fortune_tickets и card_level/account_level имеют расхождения. Сохранить исходные значения в миграционном архиве; определить единую семантику по всем местам использования до преобразования. Не складывать или заменять поля без отчёта.
- Зафиксировать единицы каждого временного поля; привести связанные операции к одному контракту и преобразовать данные явно.
- Любая строка, не проходящая целевые ограничения, попадает в отчёт с исходным значением. Миграция не считается принятой при потерянных строках или необъяснённых расхождениях.
- Автообновление хостинга выполняет git pull при запуске. С 2026-11-27 пользователь разрешил публиковать проверенные этапы в отслеживаемую ветку для тестового стенда. Каждый этап — отдельный коммит, запись в памяти, журнал ручных проверок и сверка на хостинге до следующего этапа. Первый этап проверяет соединение MySQL/MariaDB, оставляя операции в SQLite; это временный диагностический режим, а не второй изменяемый источник данных.
- До новых записей в MySQL можно вернуться к неизменённому снимку SQLite. После новых записей требуется перенос изменений обратно или восстановление согласованной версии данных; одного отката Git недостаточно.

## Приёмка

Проверить импорт дважды в отдельных чистых тестовых схемах. Сравнить число строк, ключи, нормализованные значения и суммы, имущество каждого игрока и контрольные суммы истории. Проверить 20–50 конкурирующих операций через ограниченный пул, повтор платежа/кнопки/выплаты, ошибку между debit/credit, перезапуск на каждой стадии расчёта, таймауты и восстановление соединения. Полноценные Telegram-проверки и браузерные проверки Mini App учитываются отдельно от имитации событий.
