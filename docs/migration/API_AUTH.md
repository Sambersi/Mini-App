# Авторизация API в подготовленной ветке

Реализация следует [проверке initData в документации Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app). Строка initData передаётся в заголовке Authorization со схемой tma; она не берётся из initDataUnsafe. Проверяются HMAC, отсутствие повторяющихся полей, auth_date (24 часа, допуск часов вперёд 30 секунд) и корректный ID пользователя. Не прошедшие проверку запросы получают общий ответ 401, без утечки токена или деталей подписи.

Профиль и количество билетов доступны владельцу подтверждённого ID. У бонуса и колеса отправитель берётся из подтверждённой личности, попытка указать другого игрока отклоняется. Журналы требуют административных прав сервера; callerId из query не является доказательством прав. admin/check больше не возвращает безусловное true.

Plain-клиент передаёт initData только запросам /api/ того же origin, без пересылки авторизации внешним адресам. React-клиент добавляет заголовок в собственном API-адаптере; сборка выполнена. HTML страницы backup только перенаправляет и не вызывает API, отдельный загрузчик ей не добавлялся. Оформление Mini App не переписывалось, подтверждение его работы в настоящей WebView остаётся отложенным.

Это код feature-ветки stage03-runtime. Хостовый релиз до публикации продолжает использовать прежнюю реализацию; не считать его API защищённым по факту наличия этого документа. Реальное подключение к новым репозиториям, атомарность веб-бонуса/колеса и итоговая Telegram-проверка ещё необходимы. Аутентификация сама по себе не делает начисления атомарными и не защищает операцию от повтора.

Проверки: модификация подписи и пользователя, истёкшая/будущая дата, повтор полей, подмена владельца/администратора, запрет отправки initData внешнему origin. Подписи в тестах синтетические, реальный токен не используется.
