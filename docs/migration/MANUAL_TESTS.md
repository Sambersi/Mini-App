# Журнал изменённых сценариев

## REFERRER-BANK-01 — начисление и снятие (feature, 2026-11-28)

- `реф` → «🏦 Снять банк» (`withdraw_referrer_bank`); отдельный экспортированный обработчик в referralSystem тоже передаёт update_id. Игрок с накопленным банком. Ожидание: банк обнуляется и PF зачисляется вместе с журналом; два одновременных запроса не зачисляют один остаток дважды. Повтор того же update возвращает receipt, новое событие при пустом банке сообщает об отсутствии средств. Потолок обычной покупки при этом не добавлен, как в исходном прямом UPDATE.
- Начисление от выигрыша Double: процент по числу рефералов из config, floor целого бонуса, лимит 25000 PF, избыток сгорает. Старый уже превышенный банк не уменьшается, added не становится отрицательным. Вызов целого выигрыша Double ещё в следующем пакете: перенос банка сам не делает payout готовым.
- Дробный исторический банк при снятии не округляется и не теряется: операция отклоняется до отдельной сверки. SQL-ошибка после обнуления/зачисления/журнала откатывает всё. Первый SQL-прогон выявил неверное связывание счётчика рефералов; исправлено и повторено полностью.
- Автопроверки: 129 локальных тестов, 221 SQL-сценарий MariaDB, 76 сравнений и полные профили. Новые 10 сценариев: повторы, 20 разных начислений, 20 разных снятий/одно успешное, границы/сгорание, дробь, SQL rollback. Ручной статус: ожидает общего runtime; настоящий Telegram не проверен, master SQLite. Для нового settlement требуется явный стабильный ключ creditReferrerBank; старый addToReferrerBank сам не дедуплицирует выигрыш.

## DOUBLE-BET-01 — приём ставки и состояние (feature, 2026-11-28)

- Чат с Double: `банк`; `2/3/5/игра/game <сумма/всё/все/к>`; команды множителей без суммы → предложенные суммы → `bet_<x2|x3|x5|GAME>_<amount>`. Точные алиасы исходного handlers/double.js сохранены, парсер суммы не переписывался. Кнопка из отключённого Double-чата теперь отвергается сервисом; произвольный xN тоже отвергается.
- Ожидание: одна ставка/одно списание/один max_bet и журнал; повтор одного update не создаёт второй расход. Новый клик с новым update после cooldown — новая ставка по прежней механике. Несколько самостоятельных GAME разрешены; cooldown 1 секунда на игрока+множитель общий между чатами и переживает restart. Недостаток PF, бан, смена раунда, закрытие приёма не расходуют деньги.
- Проверить границу 5 секунд до конца обычного результата и 20 секунд при результате GAME, для всех множителей. Недоступный/завершённый паспорт не принимает ставку, даже если сохранённый state ошибочно ACCEPTING. Большие суммы не округляются в новом сервисе, отдельного возврата после SQL-ошибки нет — транзакция откатывается.
- `банк`/админские логи/статистика используют перенесённые выборки; окончательная выплата/статистика ещё в следующем пакете. Повреждённый JSON состояния не заменяется новым раундом. Уведомления хранят прежние ключи/7 дней retention; фактическая доставка Telegram после падения не проверена.
- Автопроверки: 128 локальных тестов; 211 SQL-сценариев MariaDB, 76 сравнений и полные профили. 13 новых сценариев включают повторы/гонки по 20, закрытие/бан/чат, две SQL-ошибки после дебета/журнала, состояние/retention/точность и завершённый паспорт. Ручной статус: ожидает полного runtime и завершения payout; master остаётся SQLite, настоящего Telegram-прогона нет. Старые неоднозначные pending-выплаты автоматически не выплачивались.

## BOSS-COMBAT-01 — целая атака и создание босса (feature, 2026-11-28)

- Администратор / Тех администратор / MAIN_ADMIN: `новый_босс <имя> <файл> <HP> balance <приз>`; имя по прежнему фиксируется как «Математика». Проверить отказ чужой роли, неподдерживаемых coins/gold и дробного PF до сброса; повтор update не создаёт второго босса/второго снижения силы. Предыдущий урон сохраняется в boss_damage_history перед очисткой.
- `бос` / `босс` / `👾 босс` / `боссс` → «⚔️ Атака» (`attack_boss`) → `attack_boss_<index>` → следующий вопрос / «↩️ Назад в меню» (`back_to_boss_handler`). Проверить разные чаты/игроков, старое меню, несколько меню, повтор одной кнопки и одновременный последний удар двух игроков. Старые импортированные меню без версии требуют нового открытия; отказ не списывает энергию.
- Ожидание: один ответ — одна энергия и одно изменение HP/урона/серии/прочности. Просроченный правильный ответ теперь не наносит урон (исправление), серия сбрасывается; неуспешный ответ расходует прочность с первого раза, Кулак/бесконечное оружие не ломаются. Сломанное удаляется и заменяется Кулаком. Пятый правильный ответ ×2; старое оружие ×0.1 с floor, Ручка/Бумажка/Указка без снижения. Фаза 1: 4 варианта, фаза 2: 8; финальный удар и награда атомарны.
- Проверить начальный таймер 10 секунд, снижение до 6 по серии, запаздывание Telegram, повторную привязку и старый таймер. Отсчёт начинается при первой привязке отправленного сообщения, повтор не продлевает. Таймер обновляется каждые 2 секунды при исходном открытии; бесконечная автоматическая цепочка вопросов не вводилась. После restart сервер проверяет срок сохранённого вопроса, таймер в памяти сам не восстанавливается.
- Автопроверки: 126 локальных тестов; 198 SQL-сценариев MariaDB, 73 сравнения и полные профили. 17 новых сценариев покрывают перечисленные гонки/права/часы/бан, SQL rollback финального удара вместе с выплатами и rollback создания. Telegram проверен имитацией, настоящий клиент/падение процесса в середине атаки ещё не проверены. Сообщения компактнее старой рамки, кнопки и маршруты сохранены. Ручной статус: ожидает полного runtime; master SQLite. Уведомления после commit, outbox доставки после падения пока отсутствует.

## BOSS-REWARDS-01 — награда за босса (feature, 2026-11-28)

- `босс` / `👾 босс` / `боссс` → `attack_boss` → ответы на вопросы → финальный удар второй фазы → отчёт администратору и уведомления игрокам. Целый удар ещё переносится; текущая проверка относится к сервису раздачи, не к готовому сквозному маршруту.
- Ожидание: каждому из исходных первых 25 строк топа выдаётся полная фиксированная награда, включая игроков с нулевым уроном по прежней семантике. Повтор boss_id не начисляет/не уведомляет заново; редактирование приза после выплаты не меняет сохранённый результат. При SQL-ошибке в середине раздачи нет частично оплаченного списка. Отказ личного сообщения не отменяет выплату и отдельно отражается в отчёте.
- Отказы: живой босс, старый ID после смены текущего босса, неизвестный приз/coins/gold, переполнение. Уже побеждённый исторический SQLite-босс без подтверждённой истории выплат не получает автоматическую новую раздачу; требуется отдельная сверка. Награда не получает лимит обычной покупки. Сумма берётся из БД, переданный fixedPrizeAmount её не подменяет.
- Автопроверки: 121 локальный тест, два полных прогона хоста по 181 SQL-сценарию, 73 сравнения и все профили. Новые 8: 20 повторов, старый receipt, живой босс/тип приза, инвентарь, SQL rollback второго получателя и успешный повтор, исторический запрет. Telegram-адаптер проверен имитацией без отправок; доставки после падения между commit и DM пока нет. Ручной статус: ожидается после полного runtime и завершения целой атаки; master SQLite.

Второй новый запрос того же товара отклоняется, включая старое строковое JSON-владение. Проверить бесплатное и бесконечную прочность -1, нехватку PF, неизвестный товар. Актуальная цена берётся из каталога при покупке, прежний callback не фиксирует показанную цену.

Новые 8 сценариев: повторы/гонка по 20, строковый дубль, конфликт/товар/валюта, бесплатная покупка, PF-отказ, SQL rollback после дебета и после журнала. Адаптер — имитация Telegram без отправок. Ручной статус: ожидается после общего runtime; master всё ещё SQLite. Целая атака и награды босса ещё в работе.

## FINANCE-LOGS-01 — журнал и плановая очистка (feature, 2026-11-28)

- Mini App → админка → финансовый журнал (`/api/admin/logs/finance`) → тип события → поиск Telegram ID / игрового numeric_id → следующая/предыдущая страница → выбор даты → сброс даты. Право администратора и Telegram initData проверяются существующим middleware; обычный игрок не получает журнал.
- События для проверки: `передать`/`перевести`; административные выдача/снятие/установка предмета; `бан`/`разбан`, `мут`/`размут`, `кик`; активация промо. Конкретные механики ещё требуют завершения своих составных операций, перенос записи журнала сам по себе их готовность не подтверждает.
- Ожидание: верные участники/имена/numeric_id, сумма/валюта/успех/отказ/payload; поиск находит актёра и получателя, неизвестный игрок не ломает строку. Страницы и переход к дате сохраняют фильтры, одинаковые времена упорядочены по ID убыванию. Сумма вне точности Number остаётся строкой без округления в API.
- Плановая задача при запуске и каждый час: message_log 30 дней, finance_log 365, Double и Dice журналы 90; точная граница срока остаётся. Очистка двух Dice-таблиц откатывается целиком при SQL-ошибке. Это прежний retention, не удаление архивного снимка/кошелькового журнала.
- Автопроверки: 116 локальных тестов, 146 SQL-сценариев, 73 сравнения со снимком и все профили; включены фильтры, поиск обеих сторон, страницы/дата, SQL rollback журнала и очистки, retention. Ручной статус: ожидается после полного подключения runtime; настоящие Telegram/WebView-запросы не выполнялись. Хост остаётся SQLite, feature проверена на отдельной MariaDB `_checks`.
