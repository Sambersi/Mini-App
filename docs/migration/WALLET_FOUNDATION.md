# Этап 3.1: основа денежных операций

Пользователь 2026-11-27 подтвердил ручной пакет этапа 2 («все работает») и разрешил продолжить. Подготавливаемый модуль не подключён к командам и API. Бот продолжает работать с SQLite; переключение требует переноса всех активных вызывающих цепочек.

## Прослеженные цепочки

| Вход | Обработчик и зависимость | Поведение, которое сохранить |
|---|---|---|
| `профиль` / `проф` → управление → назад | bot.js → handlers/profile.js → getUserById | Профиль, имущество, настройки; manage_profile/back_to_profile |
| `карта` / `карты`; `финансы` → карта | handlers/cardInfo.js → getCardDetails, generateCardImage, скины | Номер карты, изображение, навигация; manage_card/card_info/back_to_card_menu |
| `пополнить [сумма]`; инструкция → topup_all | bank/cardTopUp.js → performCardTopUp | PF main → PF card; проверка полной запрошенной суммы, затем частичное пополнение до лимита карты по account_level |
| `снять [сумма]`; инструкция → withdraw_all | bank/cardTopUp.js → performCardWithdrawal | PF card → PF main; частичная сумма до лимита main 250M/251M/252M/253M при уровнях <10/10/15/20 |
| Перевод по команде или ответу | bank/bankTransfers.js → performTransfer | Проверки ЧС, обеих карт, блокировок переводов, прав администратора и особых категорий, лимита карты получателя; журнал и уведомления |

Это частичная карта. Middleware, все алиасы переводов, API и фоновые потребители ещё требуют разбора перед подключением. Персональные исключения лимитов сохраняются в исходниках, в документацию ID не копируются.

В старых пополнении/снятии/переводах используется синхронный SQLite transaction с async callback. Новый withTransaction ожидает callback, commit и rollback на одном выделенном соединении. Повторный `card` в bot.js:4032/4184 имеет одинаковые проверки и обработчик; удаление и проверки достижимости пока не выполнены.

## Что реализовано

- src/services/walletMovement.js — внутренняя бухгалтерская операция между двумя существующими кошельками одной валюты; права и правила команд подключаются будущими адаптерами.
- src/repositories/wallets.js — блокировка строк в стабильном порядке, оба остатка и две проводки на том же соединении.
- Миграция 003 — wallet_operations с уникальным ключом и хешем запроса, сохранённый результат; source_run_id журнала допускает NULL для новых операций. Ключи операций сравниваются с учётом регистра.
- Все суммы через BigInt и строки, без округления Number; предотвращены отрицательные остатки и переполнение BIGINT. Доступная сумма для `all` и вместимость получателя вычисляются под блокировками.
- Повтор ключа с тем же запросом возвращает исходный результат; другой запрос с тем же ключом отклоняется. Ошибка откатывает обе проводки и остатки. Неоднозначный сбой commit не вызывает автоматического повтора; соединение уничтожается, повтор возможен с тем же ключом.

## Проверка на хостинге

Создана отдельная БД с суффиксом `_checks` во втором слоте хостинга. MYSQL_TEST_* хранятся только в приватных .env. scripts/check-wallets.cjs отказывается работать с MYSQL_DATABASE или базой без указанного суффикса и с непустой таблицей игроков. Синтетические игроки и проводки удаляются после прогона; реальные пользовательские данные не загружаются.

Локально: npm test — 37 пройдено, 0 пропущено. Интеграционный прогон на MariaDB: ожидается. Проверяет точность >2^53, повтор ключа, конфликт запроса, частичную сумму, недостаток средств, SQL-ошибку после debit, 20 одинаковых и 20 конкурирующих запросов, `all` и верхнюю границу BIGINT.

Ручные сценарии этого пакета: команды игроков не менялись. Повторные покупки, платежи, лимиты/права переводов и восстановление игровых выплат этим модулем ещё не проверены. Следующий шаг — рабочая схема карточных реквизитов/правил и адаптеры финансовых команд с теми же ограничениями; общее переключение runtime пока запрещено.
