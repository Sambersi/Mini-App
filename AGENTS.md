# Работа с myBot

Перед работой прочитать docs/PROJECT_STATE.md. Для миграции также прочитать docs/migration/PLAN.md, docs/migration/HOST_CHECKPOINTS.md и docs/migration/MANUAL_TESTS.md; маршруты искать в docs/migration/ROUTES.md и исходниках. Факты документации сверять с текущим коммитом. Новые указания пользователя имеют приоритет.

## Сохранение поведения

- Сохранять игроков, деньги, инвентарь, историю, публичные команды, алиасы, роли, ограничения и навигацию. Намеренные изменения механик фиксировать отдельно.
- Перед удалением дубля проверить регистрацию, порядок middleware, тип чата, права и побочные эффекты. Не считать неиспользуемой функцию только по отсутствию прямого вызова: учитывать callback, регулярные выражения, динамические импорты, API и задачи.
- После изменений операций БД обновлять ручной журнал: команда → кнопки → роль/условия → ожидаемый результат → выполненные автопроверки → ручной статус. Не помечать запланированное как проверенное.

## Работа с данными

- Для тестов использовать отдельную БД. Импорт db.js сейчас изменяет схему и справочники; не использовать его для read-only обследования рабочей базы.
- Не публиковать секреты и данные игроков в коде, логах проверок, документации и Git. Не менять общую конфигурацию агента вне репозитория ради памяти этого проекта.
- Переводы, ставки, покупки и награды должны быть атомарными; повтор внешнего события не создаёт повторного начисления.
- Пользователь 2026-11-27 разрешил коммиты и push для поэтапной проверки на хостинге. Каждый этап сначала проверять локально, затем публиковать с обновлённой памятью и списком ручных проверок. Дальше следующего согласованного этапа не идти до сверки на стенде.

## Проверки и передача работы

Корневой npm test запускает node:test для tests/*.test.cjs. npm run db:check выполняет диагностический SELECT к указанной в .env MySQL/MariaDB без запуска бота. Проверки выбирать по изменению: синтаксис, сборка UI, интеграционные проверки на целевой БД, сценарии прав и конкуренции. Реальные Telegram-прогоны отделять от имитации API. Отмечать ограничения проверок.

После каждого законченного этапа обновить docs/PROJECT_STATE.md: решения, фактические изменения, команды проверок и результаты, оставшиеся дефекты и следующий конкретный шаг. Не переносить в память всю переписку.
